## 0. The four facts everything else follows from

1. **The thing that gets packed is not the module directory.** Both packages are emitted into
   `<module>/target/npm` by `build/npm-package.js` (shared emitter `ui/build/npm-package-lib.js`),
   which writes its own `package.json` — a different file from the one in the module root. The
   module-root `package.json` is the *source of record* (peer ranges, devDependencies, the `//…`
   rationale keys); the emitted one is what a consumer installs. `npm pack` must run in
   `target/npm`. From the module root it produces a 701-file tarball **under the same filename** —
   see section 7.

2. **The payload is complete at the end of `compile`.** `frontend-maven-plugin`'s `grunt` execution
   is bound to `compile` in `ui/pom.xml` `<pluginManagement>` (line 550), and `grunt build` is
   `["eslint", "npm-package"]`. The emitter reads `src/main/js`, `src/main/resources` and
   `src/main/esm` directly — never `target/classes` — so it does not depend on
   `maven-resources-plugin` or `maven-assembly-plugin`, both of which run later at `package`.

3. **`build-helper:attach-artifact` records a path, it does not read the file.** Measured: with a
   deliberately non-existent `<file>`, `mvn package` **succeeds**; the failure is deferred to
   `install`. This weakens — but does not remove — the ordering constraint in section 5.

4. **The tarball is reproducible.** The tarball `npm pack` produced by hand into a scratch
   directory and the one Maven produced through `frontend-maven-plugin` are **byte-identical**
   (`md5 5664dba7a08647130a8c830b4c5de7e4`). npm normalises mtimes and ownership, so the artifact
   does not churn between builds.

## 4. THE VERSION CHECK — two options, no recommendation made

**What happens today with no check at all** (measured, so that the cost of doing nothing is on the
record): `build-helper`'s `<file>` interpolates `${project.version}` while `npm pack` derives the
filename from `package.json`. On drift they name different files and the build fails — but at
`install`, not at `package`, with:

```

        …/target/does-not-exist.tgz
```

which says nothing about a version mismatch. Also measured: a drifted `package.json` version makes
`npm install` (bound to `initialize`) **rewrite `package-lock.json`**, so the drift dirties a
committed file as well.

### Option A — `maven-enforcer-plugin`

**Managed version: yes, but not where you would look.**

- `/home/maxim/Documents/_projects/forgerock/commons/pom.xml` **line 1007-1011** —
  `<pluginManagement>` entry `maven-enforcer-plugin` with `<version>${mavenEnforcerPluginVersion}</version>`,

  parent of `ui/pom.xml`, so both modules inherit it: the effective pom of `ui/commons` and

So an enforcer execution in either module pom needs **no `<version>`**. Shape:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-enforcer-plugin</artifactId>
    <executions>
        <execution>
            <id>check-npm-version</id>
            <phase>validate</phase>
            <goals><goal>enforce</goal></goals>
            <configuration>
                <rules>
                    <evaluateBeanshell>
                        <condition>
                            new java.util.Scanner(new java.io.File(basedir, "package.json"))
                                .useDelimiter("\\Z").next()
                                .matches("(?s).*\"version\"\\s*:\\s*\"${project.version}\".*")
                        </condition>
                        <message>package.json version != ${project.version}</message>
                    </evaluateBeanshell>
                </rules>
            </configuration>
        </execution>
    </executions>
</plugin>
```

Cost, recorded honestly: **`maven-enforcer-plugin` is not in `~/.m2` at all** — the directory
`~/.m2/repository/org/apache/maven/plugins/maven-enforcer-plugin/` does not exist. It is managed
but has never been resolved in this repository, so adding it means a first download, and an
offline build (`mvn -o`) fails until it is cached. **This option was therefore not executed** — the
snippet above is written but unmeasured. Upside: it runs at `validate`, the earliest phase there
is, before node is installed and before `npm install` reads the drifted version.

### Option B — a two-line node script through the existing `frontend-maven-plugin`

No new plugin, no download, works offline. **Measured working, and measured failing on drift.**

`<module>/build/check-version.js` — the two lines:

```js

if (pkg.version !== process.env.PROJECT_VERSION) { console.error("[check-version] package.json " + pkg.version + " != project.version " + process.env.PROJECT_VERSION); process.exit(1); }
```

`<module>/package.json` gains one script entry:

```json

```

and the module pom gains one execution inside the `frontend-maven-plugin` block:

```xml

    <id>check-npm-version</id>
    <goals><goal>npm</goal></goals>
    <phase>initialize</phase>
    <configuration>
        <arguments>run check:version</arguments>
        <environmentVariables>
            <PROJECT_VERSION>${project.version}</PROJECT_VERSION>
        </environmentVariables>
    </configuration>
</execution>
```

Measured, happy path:

```
[INFO] --- frontend:1.15.0:npm (check-npm-version) @ commons ---
[INFO] > node build/check-version.js
[INFO] BUILD SUCCESS
```

Measured, drift (`package.json` temporarily set to `9.9.9-SNAPSHOT`):

```
[INFO] [check-version] package.json 9.9.9-SNAPSHOT != project.version 3.2.0-SNAPSHOT
[INFO] BUILD FAILURE
[ERROR] Failed to execute goal com.github.eirslett:frontend-maven-plugin:1.15.0:npm
        (check-npm-version) on project commons: … Process exited with an error: 1
```

Two things a reader needs to know before choosing this one:

- **`frontend-maven-plugin` 1.15.0 has no `node` goal.** Measured — the available goals are
  `bower, bun, ember, grunt, gulp, install-bun, install-node-and-npm, install-node-and-pnpm,
  install-node-and-yarn, jspm, karma, npm, npx, pnpm, webpack, yarn`. The check has to go through

  To get it in front of `npm install` the execution has to be added to `ui/pom.xml`'s
  `<pluginManagement>` block between `install-node-and-npm` and `npm-install` instead — at the cost
  of applying to every `ui` module, including `mock`, which has no such check to make.

Both options are recorded. **Not choosing between them is deliberate.**

**Last in `<plugins>`, immediately before `</plugins>`** — line 113 in `ui/commons/pom.xml`,

```

[INFO] npm notice filename: openidentityplatform-ui-commons-3.2.0-SNAPSHOT.tgz
[INFO] npm notice total files: 200

[INFO] --- build-helper:3.6.1:attach-artifact (attach-npm-tarball) @ commons ---
```

**Counter-test, and it is not what one would assume.** With `build-helper` declared *before*
`frontend-maven-plugin`, `attach-artifact` runs before `npm-pack` — and the build still succeeds,
including `install`. `attach-artifact` only records a `File` on the project; `maven-install-plugin`

`BUILD SUCCESS` for `mvn package`, and fails only at `install`.

So the ordering is a **robustness and legibility** constraint, not a correctness one *as currently
wired*. It becomes a correctness one the moment anything reads the attached-artifact list inside
`package` (an assembly `moduleSet`, a shade, a signing step), or if `npm-pack` is ever moved to a
later phase than `attach-artifact`. Declaring it last costs nothing and removes the trap.

Packing, not publishing. Licence and `repository`-field questions are task 3.11's and are not
raised here; `"private": true` is **correct for this task and must stay** — `npm pack` honours it
and only `npm publish` refuses, which is exactly the property design decision D18 relies on.

**Verdict: nothing breaks `npm pack` as it is used here. One live trap in the wiring.**

| checked | result |

| `"files"` too narrow | No. Emitted `"files"` is `["amd","esm","www","LICENSE.md","MANIFEST.txt","NPM-PACKAGE.md"]`; tarball vs `expected-payload.txt` diff is empty both ways, both modules. |
| `prepack` / `prepare` / `postpack` script | None. **The trap — `workingDirectory` is load-bearing.** `npm pack` from the module root

one way to get a wrong tarball out of a correct source tree, which is why the

## 11. Method

Every number in this file came from a command; nothing is quoted from another document without
being reproduced.

1. **Pack.** `npm pack --pack-destination <scratch>` run in `ui/commons/target/npm` and
   `ui/user/target/npm`. Both tarballs and every scratch tree deleted afterwards.
2. **Payload diff.** `tar -tzf`, `grep -v '/$'`, `sed 's|^package/||'`, `LC_ALL=C sort`, against
   `<module>/build/expected-payload.txt` with comments and blanks stripped; `LC_ALL=C comm -23` /
   `-13` both directions. `LC_ALL=C` per the warning in `MANIFEST.txt`'s own header.
3. **Composition diff.** Both tarballs extracted, `amd/` then `www/` copied into one overlay
   directory (commons first, user second), `find -type f` vs the unpacked
   `org.openidentityplatform.commons.ui.user-www.zip`.
4. **Phase.** `rm -rf ui/commons/target/npm` then `mvn -o -DskipTests compile`; `find | wc -l`.
   Never `mvn clean`.
5. **Wiring.** Poms edited in place, `mvn -o -DskipTests install` in each module, execution order
   read off the `[INFO] --- plugin:goal (id) ---` lines. Counter-tests: `build-helper` moved ahead
   of `frontend`; `<file>` pointed at a non-existent path for both `package` and `install`.
6. **Version check.** Option B implemented for real (temporary `build/check-version.js` +
   `scripts` entry, both removed), run green, then `package.json` temporarily set to
   `9.9.9-SNAPSHOT` and run red. `package-lock.json`, which `npm install` rewrote during the drift
   test, restored with `git checkout`.
7. **Managed versions.** `mvn -o help:effective-pom -Doutput=…` in both modules; `grep -n` for
   `build-helper` and `maven-enforcer-plugin`; surrounding XML read to establish whether each hit
   was `<pluginManagement>` or the m2e `lifecycle-mapping` block.
8. **`dependencyManagement`.** Sibling entries applied to the root pom, effective pom regenerated,
   the four managed keys enumerated with ElementTree, root pom reverted with `git checkout`.
9. **Revert.** Both module poms restored from byte copies taken before the first edit; root pom
   and `package-lock.json` restored with `git checkout`; `git status --short` empty.
